# STEP-016: ADM2 시/군/구 확장 검토

## 목표

- 도/주 단위 이후 시/군/구 단위까지 내려가는 확장 가능성을 검토하고, 적용 범위를 결정한다.

## 작업 범위

- ADM2 데이터 크기와 렌더링 성능을 확인한다.
- 모든 국가 지원 대신 우선 지원 국가 범위를 정한다.
- 모바일에서 ADM2 경계가 너무 복잡하게 보이지 않는지 확인한다.
- 시/군/구 선택 UX가 필요한지, 검색 또는 리스트 보조 UI가 필요한지 검토한다.
- 실제 날씨 API 연동 시 지역 좌표 기반 조회 방식과 연결 가능성을 확인한다.

## 완료 기준

- ADM2를 바로 구현할지, 특정 국가만 지원할지 판단 기준이 정리된다.
- 성능과 UX 리스크가 문서화된다.
- 이후 구현 Step으로 나눌 수 있는 작업 단위가 정리된다.
- 기존 ADM1 지도 구조를 해치지 않는 확장 방향이 정리된다.

## 검토 결과

### 데이터 소스 및 크기

- ADM2도 Step 014와 동일하게 geoBoundaries API `current/gbOpen/{ISO3}/ADM2/`를 우선 후보로 유지한다.
- geoBoundaries global download 안내 기준 ADM2 전체 GeoJSON은 약 500MB 규모로, 클라이언트에서 전 세계 데이터를 한 번에 다루는 방식은 MVP에 적합하지 않다.
- 2026-06-02 기준 current API 샘플 확인 결과:
  - `KOR` ADM2: 약 1.2MB, 228개 feature
  - `USA` ADM2: 약 10.5MB, 3,233개 feature
  - `JPN` ADM2: 약 10.9MB, 1,742개 feature
  - `FRA` ADM2: 약 124.2MB

### 판단

- ADM2는 전 국가 즉시 지원 대신, 국가별 allowlist 기반 단계적 지원으로 진행한다.
- 1차 후보는 `KOR`, `USA`, `JPN`으로 제한한다.
- `FRA`처럼 100MB를 넘는 국가는 클라이언트 직접 fetch/render 대상에서 제외하고, 단순화 데이터 또는 서버 캐싱/타일링 검토 이후 지원한다.

### 성능 리스크

- ADM2는 feature 수가 많아 지도 회전/줌 중 SVG path가 많아질 수 있다.
- 모바일에서는 경계선 밀도가 높아 시각적 노이즈가 커지고 터치 타깃이 작아진다.
- 국가 선택 직후 ADM1과 ADM2를 동시에 표시하면 렌더링 복잡도와 선택 우선순위가 모호해진다.

### UX 방향

- 기본 지도는 ADM1까지만 즉시 표시한다.
- ADM2는 ADM1 지역 선택 이후 별도 확대 상태에서만 표시한다.
- 모바일에서는 ADM2 경계 직접 클릭만 제공하지 않고, 하단 리스트/검색 보조 UI를 함께 제공하는 방향이 적합하다.
- ADM2 선택은 실제 날씨 API 연동 시 행정구역 이름보다 중심 좌표 기반 조회와 연결하는 것이 안정적이다.

### 후속 구현 Step 제안

- `STEP-018`: 선택 ADM1 기준 ADM2 경계 표시
- `STEP-019`: ADM2 지역 선택 및 좌표 기반 mock/API 조회 연결
- `STEP-020`: 모바일 ADM2 검색/리스트 보조 UI 추가
